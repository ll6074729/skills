# 规范生成检查清单

本清单用于规范生成完成后的自检，确保生成的规范体系完整、准确，符合技能内置原则并适配项目事实。

## 一、AI 行为规范检查

- [ ] AGENTS.md 是否完整包含 5 项 AI 禁止行为？
- [ ] 每项禁止行为的细则是否完整保留？
- [ ] AI 行为门禁是否包含任务开始前、执行中、完成后三个阶段？
- [ ] 是否完整保留 AGENTS 模板中的 7 条通用强制规则，并按项目类型裁掉不适用的领域路由？
- [ ] 是否保留「禁止仅凭记忆、摘要、此前读取记录替代本次读取」？
- [ ] 是否明确该条不因使用 CodeGraph、Context7 等工具而豁免，且禁止复用上一轮工具输出？

## 二、规范体系搭建检查

- [ ] 是否采用两层治理架构（AGENTS.md + .agents/rules/）？
- [ ] AGENTS.md 是否作为路由入口，只保留规范标题、触发场景和门禁？
- [ ] 每个规则域是否定义了明确的「强制触发场景」列表？
- [ ] 是否要求场景命中时必须读取对应规则文件？
- [ ] 是否定义了规则文件缺失、无法读取或冲突时的阻断处理？
- [ ] 每个规则文件是否采用标准结构（适用范围+核心要求+验证要求+审查要求）？

## 三、技术栈适配检查

- [ ] 文件后缀`{ext}`是否全部替换为实际后缀（`.ts`/`.go`/`.py`等）？
- [ ] ORM 相关描述是否适配用户采用的 ORM？
- [ ] 依赖注入描述是否适配用户采用的框架？
- [ ] 异常处理描述是否适配用户采用的框架？
- [ ] 测试框架描述是否适配用户采用的测试工具？
- [ ] 构建工具描述是否适配用户采用的构建工具？
- [ ] 目录结构是否符合技术栈官方推荐？

## 三-A、框架内置组件适配检查

**仅当项目采用了提供相应内置能力的框架 / ORM / 测试或构建工具时执行适用项；按项目类型裁剪，不得把下列清单当成每个项目都必须生成的内容。**

- [ ] 是否询问了用户是否采用包含内置组件库的框架？
- [ ] 是否检索了框架官方文档的组件清单？
- [ ] 若用户提供了参考项目，是否提取了参考项目的组件使用约定？
- [ ] 有前端框架时，`frontend-ui.md` 是否包含经检索确认的适用组件规则？仅后端项目标记不适用。
- [ ] 有后端框架时，`backend.md` 是否包含经检索确认的适用内置能力？仅前端项目标记不适用。
- [ ] 有数据库访问 / ORM 时，`database.md` 是否包含适用的数据访问规则；无数据库时标记不适用？
- [ ] 用户选择沿用或补充自动化测试且项目有测试框架时，`testing.md` 是否写入该框架实际提供的 Mock、断言等能力？否则记录现状与缺口，不伪造框架组件。
- [ ] 有构建工具时，`dev-tooling.md` 是否写入该工具提供的适用能力？
- [ ] 前端表格、表单、弹窗、抽屉、操作列、上传下载、图标等场景是否只检查项目实际使用的能力？
- [ ] 后端 DI、守卫 / 拦截器、异常、日志、配置等场景是否只检查实际采用的后端框架能力？
- [ ] 每个规则文件的「禁止替代方案」章节是否完整，没有留空？
- [ ] 所有列出的组件名是否来自框架官方文档或权威来源？
- [ ] 组件清单是否标注了来源（Context7 官方文档、参考项目或实际使用的降级检索来源）？
- [ ] 「框架内置组件优先使用」规则是否违反技能内置原则或项目实际约束？

## 四、架构设计检查

- [ ] 模块是否支持按需启用禁用？
- [ ] 禁用模块后 UI 元素是否完全隐藏而非置灰？
- [ ] 跨模块调用是否通过公开接口契约？
- [ ] 跨模块依赖是否通过依赖注入显式注入？
- [ ] 是否拒绝无当前需求支撑的转发型抽象？
- [ ] 接口性能是否作为基础约束？

## 四-A、公共模块抽离检查

- [ ] 是否存在 ≥2 处同构流程、且差异仅为配置值的重复实现？
- [ ] 达到门槛的能力是否已抽离为公共模块，调用点只传配置？
- [ ] 公共模块是否只有一个入口，且不反向依赖任何业务模块？
- [ ] 是否避免为单处使用、业务语义不同或假设性需求做抽离？
- [ ] 需要 >5 个参数或 ≥2 个布尔开关时，是否改为拆分能力而非继续加参数？
- [ ] 上传、导入、导出、请求等高频能力是否只有一份实现？
- [ ] 每个配置变体是否有测试用例覆盖？
- [ ] 修改公共流程是否只需改一处，调用点 diff 只含配置？

## 四-B、规范自包含检查

- [ ] 是否存在用「参见/详见某文件、某链接」替代应有正文的条目？
- [ ] 是否禁止把项目内其他文本文件作为规则来源？
- [ ] 需要附加文本文件引用时，是否先询问用户并取得同意？
- [ ] 用户未同意时，是否确认规范中没有任何文本文件引用？
- [ ] 外部 URL 是否仅用于来源标注，而非替代正文？

## 五、接口与性能检查

- [ ] HTTP 方法是否与操作语义一一对应？
- [ ] 响应时间字段是否统一返回 Unix 毫秒时间戳？
- [ ] `id`与`ids`类型是否一致？
- [ ] Query 批量 ID 是否使用`ids[]`数组编码？
- [ ] 是否规避`N+1`查询？
- [ ] 高频接口是否具备分页、上限、批量获取边界？
- [ ] 接口文档元数据是否完整准确？

## 六、代码实现检查

- [ ] 运行期依赖是否通过构造函数参数逐项显式接收？
- [ ] 是否禁止`Deps`、`Options`聚合对象传递接口依赖？
- [ ] 框架生成代码是否禁止手动覆盖？
- [ ] 导出面是否最小化，仅模块内部使用的成员使用私有修饰符？
- [ ] 模块是否通过入口文件只导出公开契约？
- [ ] 调用端可见错误是否通过自定义异常+全局异常处理统一处理？
- [ ] 日志是否使用统一日志组件并携带请求上下文？
- [ ] 是否定义编译门禁和静态检查要求？
- [ ] 定时任务是否在统一调度模块管理？

## 六-A、安全与字段权限检查

- [ ] `security.md` 是否包含认证授权、数据安全、API 安全、客户端安全、安全审计五章？
- [ ] 五章内容是否全部换成本技术栈的实现，没有保留其他栈的示例？
- [ ] 越权访问、会话失效、登出是否都有显式处理？
- [ ] 敏感字段是否声明加密或脱敏方式，密钥是否禁止明文存储与提交？
- [ ] 限流、幂等、参数校验、防重放是否按本栈能力定义？
- [ ] 客户端令牌存储位置与 XSS/CSRF 防护是否明确？
- [ ] 审计日志是否覆盖登录、权限变更、数据导出等敏感操作？
- [ ] 错误响应是否禁止透出内部堆栈与实现细节？
- [ ] 字段权限是否区分读、写两类，并说明列级过滤发生在哪一层？
- [ ] 字段权限规则是否与数据权限（行级）说明各自生效顺序？

## 七、数据库与缓存检查

- [ ] SQL 是否满足幂等性要求？
- [ ] SQL 文件是否采用`{序号}-{迭代名称}.sql`格式？
- [ ] 数据是否分类分离（DDL+Seed DML 与 Mock 数据独立目录）？
- [ ] 是否禁止向自增主键表显式指定`id`值？
- [ ] 索引设计是否基于真实查询路径？
- [ ] 软删除字段规则是否清晰？
- [ ] 缓存是否说明权威数据源、一致性模型、失效触发点？
- [ ] 集群模式是否使用分布式缓存？
- [ ] 缓存失效是否在事务提交成功后触发？

## 八、测试与验证检查

- [ ] 单元测试是否自包含且顺序无关？
- [ ] 单元测试文件是否命名为`{source}.spec.{ext}`？
- [ ] Bugfix 是否强制测试覆盖？
- [ ] E2E 断言是否能证明业务结果而非仅验证元素存在？
- [ ] E2E 文件是否使用`TC{NNN}-{brief-name}`命名？
- [ ] 涉及用户可观察行为是否有 E2E 或等价自动化验证？

## 九、文档规范检查

- [ ] 目录级说明文档是否同步维护中英文镜像？
- [ ] Markdown 格式是否统一（inline code、全角标点、mermaid 图示）？
- [ ] 架构图流程图是否使用`mermaid`展示，换行使用`<br/>`？
- [ ] 是否禁止段落间`---`分割线？
- [ ] 命名约定是否包含文件命名、代码标识符、数据库命名三部分？

## 十、跨平台与工具链检查

- [ ] 开发构建测试入口是否跨平台可执行？
- [ ] 是否禁止默认依赖`bash`、`sed`、`awk`等单一平台命令？
- [ ] 长期维护工具是否优先实现为项目主语言工具？
- [ ] CLI 命令文件是否按`command-{command}.{ext}`命名？

## 十一、最佳实践整合检查

- [ ] 每项技术最佳实践是否来自 Context7 官方文档，或在 Context7 未启用 / 未覆盖时来自 WebSearch / WebFetch 等规定的降级来源？
- [ ] 检索来源是否标注日期和链接？
- [ ] 最佳实践是否与技能内置原则、用户确认和项目证据交叉核对？
- [ ] 冲突点是否在规范文档中说明处理方式？

## 十-B、语言规范检查

- [ ] 规范标题、说明文字、注释、README 推荐章节表头、预检摘要、交付摘要、提问与选项说明、表格说明列、错误提示是否均为中文？
- [ ] 技术术语、代码语法、变量名、框架与工具名、命令行、配置内容是否保留原语言？
- [ ] 是否禁止在标题、注释、表头与解释性文字中使用英文或中英混写？

## 十-A、项目技术栈预检检查

- [ ] 阶段一是否在任何技术栈预检和 WebSearch 检索前先确认了项目类型？（目录边界扫描除外）
- [ ] 是否先扫描目录结构识别多个项目边界，且未读取配置内容就推断技术栈？
- [ ] 发现多个候选项目时，是否向用户确认逐项目处理、选择部分项目或按 Monorepo 处理？
- [ ] 是否逐项目记录路径、类型和技术栈，避免合并兄弟项目的依赖？
- [ ] 是否确认了工作区配置与真实项目边界，未将“有 workspace 配置”直接等同于单一项目？
- [ ] 是否默认在各独立项目根目录生成规范，未擅自在父级容器目录写文件？
- [ ] 启用工作流时是否确认覆盖项目，并逐项目映射规则和验证命令？
- [ ] 是否对每个项目明确询问测试需求和 CI/CD 需求（沿用 / 本次补充 / 暂不纳入），而非仅凭现有配置判断？
- [ ] 若用户选择暂不新增自动化测试或 CI/CD，是否记录缺口且未虚构工具、pipeline 或命令？
- [ ] 若用户暂不新增测试但选择完整 TDD 工作流，是否明确指出冲突并请用户补齐测试能力或改选工作流模式？
- [ ] 是否通过 AskUserQuestion 询问了项目类型（全栈/仅前端/仅后端）？
- [ ] 项目类型确认后是否根据类型过滤了预检文件清单？
- [ ] 仅前端项目是否跳过了 go.mod、pom.xml 等后端配置文件检查？
- [ ] 仅后端项目是否跳过了 vite.config.* 等前端配置文件检查？
- [ ] 预检结果摘要中是否标注了项目类型？
- [ ] 阶段一是否在 WebSearch 检索前先执行了项目技术栈预检？
- [ ] 是否使用 Glob 扫描了项目根目录的配置文件？
- [ ] 是否检查了 package.json、go.mod、pom.xml 等关键配置文件？
- [ ] 是否使用 Read 读取了已存在的配置文件并提取技术栈信息？
- [ ] 是否使用 LS 检查了项目目录结构以推断技术栈？
- [ ] 若项目已有技术栈，是否向用户复述确认了识别到的技术栈？
- [ ] 已识别的维度是否不再重复询问？
- [ ] 未识别的维度是否仍按动态检索流程询问？
- [ ] 询问选项是否优先推荐与已有技术栈兼容的方案？
- [ ] 若配置文件包含版本号，是否通过 Context7 或其规定的降级来源核验了版本与对应文档？
- [ ] 若项目为空（无配置文件），是否明确告知用户并按完整动态流程执行？
- [ ] 若部分识别，是否复述已识别部分并对未识别部分执行动态询问？
- [ ] 是否禁止凭空假设技术栈？

## 十一-A、动态学习与实时检索检查

- [ ] 阶段一是否对每个适用技术维度按工具开关执行了 Context7 检索，或使用 WebSearch / WebFetch 降级？

- [ ] 若首轮检索不充分，是否进行了多轮深度检索？
