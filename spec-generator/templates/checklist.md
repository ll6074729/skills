# 规范生成检查清单

本清单用于规范生成完成后的自检，确保生成的规范体系完整、准确、符合指南原则。

## 一、AI 行为规范检查

- [ ] AGENTS.md 是否完整包含 5 项 AI 禁止行为？
- [ ] 每项禁止行为的细则是否完整保留？
- [ ] AI 行为门禁是否包含任务开始前、执行中、完成后三个阶段？
- [ ] 通用强制规则是否完整保留（6 条）？

## 二、规范体系搭建检查

- [ ] 是否采用两层治理架构（AGENTS.md + .agents/rules/）？
- [ ] AGENTS.md 是否作为路由入口，只保留规范标题、触发场景和门禁？
- [ ] 每个规则域是否定义了明确的「强制触发场景」列表？
- [ ] 是否要求场景命中时必须读取对应规则文件？
- [ ] 是否定义了规则文件缺失、无法读取或冲突时的阻断处理？
- [ ] 每个规则文件是否采用标准结构（适用范围+核心要求+验证要求+审查要求）？

## 三、技术栈适配检查

- [ ] 文件后缀`{ext}`是否全部替换为实际后缀（`.ts`/`.go`/`.py`等）？
- [ ] ORM 相关描述是否适配用户采用的 ORM？
- [ ] 依赖注入描述是否适配用户采用的框架？
- [ ] 异常处理描述是否适配用户采用的框架？
- [ ] 测试框架描述是否适配用户采用的测试工具？
- [ ] 构建工具描述是否适配用户采用的构建工具？
- [ ] 目录结构是否符合技术栈官方推荐？

## 三-A、框架内置组件适配检查

**仅当用户采用了包含内置组件库的框架时执行本检查**

- [ ] 是否询问了用户是否采用包含内置组件库的框架？
- [ ] 是否检索了框架官方文档的组件清单？
- [ ] 若用户提供了参考项目，是否提取了参考项目的组件使用约定？
- [ ] `frontend-ui.md` 是否包含「组件使用要求」章节？
- [ ] `frontend-ui.md` 是否明确列出了各功能场景必须使用的内置组件？
- [ ] 表格组件是否明确指定（如`useVbenVxeGrid`+`Page`）？
- [ ] 表单组件是否明确指定（如`useVbenForm`）？
- [ ] 弹窗组件是否明确指定（如`useVbenModal`）？
- [ ] 抽屉组件是否明确指定（如`useVbenDrawer`）？
- [ ] 操作列组件是否明确指定（如`ghost-button`+`Popconfirm`）？
- [ ] 上传下载方式是否明确指定（如`Upload.Dragger`+`requestClient.download`）？
- [ ] 图标组件和命名格式是否明确指定（如`IconifyIcon`+`ant-design:xxx-outlined`）？
- [ ] 全局组件注册位置是否明确指定（如`src/components/global/`）？
- [ ] 适配器层目录是否明确指定（如`src/adapter/`）？
- [ ] `backend.md` 是否包含「框架内置能力优先使用」章节？
- [ ] 依赖注入装饰器是否明确指定（如`@Injectable`、`@Module`）？
- [ ] 守卫/拦截器是否明确指定（如`Guard`、`Interceptor`）？
- [ ] 异常处理基类是否明确指定（如`HttpException`）？
- [ ] 日志组件是否明确指定（如`Logger`、`glog`）？
- [ ] 配置管理方式是否明确指定（如`@Inject(config.KEY)`）？
- [ ] `database.md` 是否包含「ORM 内置功能优先使用」章节？
- [ ] 实体定义方式是否明确指定（如`@Entity`+`@Column`）？
- [ ] 查询方式是否明确指定（如`QueryBuilder`）？
- [ ] 软删除方式是否明确指定（如`@DeleteDateColumn`）？
- [ ] 自动时间维护是否明确指定（如`@CreateDateColumn`）？
- [ ] `testing.md` 是否包含「测试框架内置工具优先使用」章节？
- [ ] Mock 工具是否明确指定（如`jest.fn()`）？
- [ ] 断言库是否明确指定（如`expect().toBe()`）？
- [ ] 每个规则文件的「禁止替代方案」章节是否完整，没有留空？
- [ ] 所有列出的组件名是否来自框架官方文档或权威来源？
- [ ] 组件清单是否标注了来源（官方文档、参考项目、WebSearch 检索结果）？
- [ ] 「框架内置组件优先使用」规则是否违反指南的禁止性规则？

## 四、架构设计检查

- [ ] 模块是否支持按需启用禁用？
- [ ] 禁用模块后 UI 元素是否完全隐藏而非置灰？
- [ ] 跨模块调用是否通过公开接口契约？
- [ ] 跨模块依赖是否通过依赖注入显式注入？
- [ ] 是否拒绝无当前需求支撑的转发型抽象？
- [ ] 接口性能是否作为基础约束？

## 五、接口与性能检查

- [ ] HTTP 方法是否与操作语义一一对应？
- [ ] 响应时间字段是否统一返回 Unix 毫秒时间戳？
- [ ] `id`与`ids`类型是否一致？
- [ ] Query 批量 ID 是否使用`ids[]`数组编码？
- [ ] 是否规避`N+1`查询？
- [ ] 高频接口是否具备分页、上限、批量获取边界？
- [ ] 接口文档元数据是否完整准确？

## 六、代码实现检查

- [ ] 运行期依赖是否通过构造函数参数逐项显式接收？
- [ ] 是否禁止`Deps`、`Options`聚合对象传递接口依赖？
- [ ] 框架生成代码是否禁止手动覆盖？
- [ ] 导出面是否最小化，仅模块内部使用的成员使用私有修饰符？
- [ ] 模块是否通过入口文件只导出公开契约？
- [ ] 调用端可见错误是否通过自定义异常+全局异常处理统一处理？
- [ ] 日志是否使用统一日志组件并携带请求上下文？
- [ ] 是否定义编译门禁和静态检查要求？
- [ ] 定时任务是否在统一调度模块管理？

## 七、数据库与缓存检查

- [ ] SQL 是否满足幂等性要求？
- [ ] SQL 文件是否采用`{序号}-{迭代名称}.sql`格式？
- [ ] 数据是否分类分离（DDL+Seed DML 与 Mock 数据独立目录）？
- [ ] 是否禁止向自增主键表显式指定`id`值？
- [ ] 索引设计是否基于真实查询路径？
- [ ] 软删除字段规则是否清晰？
- [ ] 缓存是否说明权威数据源、一致性模型、失效触发点？
- [ ] 集群模式是否使用分布式缓存？
- [ ] 缓存失效是否在事务提交成功后触发？

## 八、测试与验证检查

- [ ] 单元测试是否自包含且顺序无关？
- [ ] 单元测试文件是否命名为`{source}.spec.{ext}`？
- [ ] Bugfix 是否强制测试覆盖？
- [ ] E2E 断言是否能证明业务结果而非仅验证元素存在？
- [ ] E2E 文件是否使用`TC{NNN}-{brief-name}`命名？
- [ ] 涉及用户可观察行为是否有 E2E 或等价自动化验证？

## 九、文档规范检查

- [ ] 目录级说明文档是否同步维护中英文镜像？
- [ ] Markdown 格式是否统一（inline code、全角标点、mermaid 图示）？
- [ ] 架构图流程图是否使用`mermaid`展示，换行使用`<br/>`？
- [ ] 是否禁止段落间`---`分割线？
- [ ] 命名约定是否包含文件命名、代码标识符、数据库命名三部分？

## 十、跨平台与工具链检查

- [ ] 开发构建测试入口是否跨平台可执行？
- [ ] 是否禁止默认依赖`bash`、`sed`、`awk`等单一平台命令？
- [ ] 长期维护工具是否优先实现为项目主语言工具？
- [ ] CLI 命令文件是否按`command-{command}.{ext}`命名？

## 十一、最佳实践整合检查

- [ ] 每项技术的最佳实践是否来源于 WebSearch 检索？
- [ ] 检索来源是否标注日期和链接？
- [ ] 最佳实践是否与指南原则交叉验证？
- [ ] 冲突点是否在规范文档中说明处理方式？

## 十-B、语言规范检查

- [ ] 所有规范文档的章节标题是否使用中文？
- [ ] 所有解释性文字、说明文字、标注是否使用中文？
- [ ] 代码注释（行内注释和块注释）是否使用中文？
- [ ] README.md 中生成的推荐 Skills 章节表头是否使用中文？
- [ ] README.md 中生成的推荐 Skills 章节说明文字是否使用中文？
- [ ] 预检结果摘要是否使用中文？
- [ ] 交付内容（文件清单、技术栈摘要、检查清单报告）是否使用中文？
- [ ] AskUserQuestion 询问的问题和选项说明是否使用中文？
- [ ] 表格中的说明性内容（非代码标识符列）是否使用中文？
- [ ] 错误提示和降级说明是否使用中文？
- [ ] 技术术语、代码语法、变量名、函数名是否保留原语言不变？
- [ ] 框架/库/工具的专有名称是否保留原语言不变？
- [ ] 命令行指令是否保留原语言不变？
- [ ] 配置文件内容是否保留原语言不变？
- [ ] 是否禁止在规范文档章节标题中使用英文？
- [ ] 是否禁止在代码注释中使用英文？
- [ ] 是否禁止在 README.md 推荐表格表头中使用英文？
- [ ] 是否禁止在解释性文字中混用中英文（技术术语可保留，但解释必须中文）？

## 十-A、项目技术栈预检检查

- [ ] 阶段一是否在任何预检和 WebSearch 检索前先确认了项目类型？
- [ ] 是否通过 AskUserQuestion 询问了项目类型（全栈/仅前端/仅后端）？
- [ ] 项目类型确认后是否根据类型过滤了预检文件清单？
- [ ] 仅前端项目是否跳过了 go.mod、pom.xml 等后端配置文件检查？
- [ ] 仅后端项目是否跳过了 vite.config.* 等前端配置文件检查？
- [ ] 预检结果摘要中是否标注了项目类型？
- [ ] 阶段一是否在 WebSearch 检索前先执行了项目技术栈预检？
- [ ] 是否使用 Glob 扫描了项目根目录的配置文件？
- [ ] 是否检查了 package.json、go.mod、pom.xml 等关键配置文件？
- [ ] 是否使用 Read 读取了已存在的配置文件并提取技术栈信息？
- [ ] 是否使用 LS 检查了项目目录结构以推断技术栈？
- [ ] 若项目已有技术栈，是否向用户复述确认了识别到的技术栈？
- [ ] 已识别的维度是否不再重复询问？
- [ ] 未识别的维度是否仍按动态检索流程询问？
- [ ] 询问选项是否优先推荐与已有技术栈兼容的方案？
- [ ] 若配置文件包含版本号，是否 WebSearch 检索了版本是否为最新？
- [ ] 若项目为空（无配置文件），是否明确告知用户并按完整动态流程执行？
- [ ] 若部分识别，是否复述已识别部分并对未识别部分执行动态询问？
- [ ] 是否禁止凭空假设技术栈？

## 十一-A、动态学习与实时检索检查

- [ ] 阶段一是否对每个适用技术维度都执行了 WebSearch 实时检索？
- [ ] 是否根据项目类型跳过了不适用的维度（如仅前端跳过数据库维度）？
- [ ] 每次询问是否基于检索结果动态生成选项（而非固定选项）？
- [ ] 每次询问是否提供至少 3 个选项？
- [ ] 每次询问是否支持用户自定义输入（Other）？
- [ ] 检索关键词是否包含当前年份？
- [ ] 后端技术等可能存在知识盲区的领域是否通过 WebSearch 建立了知识基础？
- [ ] 若首轮检索不充分，是否进行了多轮深度检索？
- [ ] 若检索后仍无法确定主流方案，是否坦诚告知用户知识盲区并请求引导？
- [ ] 技术栈确定后是否检索并推荐了相关高质量开源项目？
- [ ] 是否推荐了至少 5 个采用相同技术组合的开源项目？
- [ ] 是否同时检索了 GitHub 和 Gitee 平台？
- [ ] 每个推荐项目是否标注了项目名、GitHub 地址、Gitee 地址（若有）、Star 数、技术栈、项目特点？
- [ ] 是否询问了用户是否采用某个开源项目作为规范参考？
- [ ] 用户选择参考项目后是否展示了 GitHub/Gitee 仓库地址？
- [ ] 是否询问了用户是否将参考项目拉取到本地进行深度分析？
- [ ] 若用户选择拉取到本地，是否询问了拉取位置和拉取平台？
- [ ] 若用户选择拉取到本地，是否成功执行了 git clone 命令？
- [ ] 若拉取失败是否降级为 WebFetch 在线分析？
- [ ] 是否禁止使用硬编码的固定技术选项列表？
- [ ] 是否禁止使用过时的技术推荐？
- [ ] 参考项目（若用户选择）是否进行了深度分析？
- [ ] 参考项目的组件使用约定是否已提取并整合到规范中？

## 十二-A、Skills 推荐与 README 更新检查
