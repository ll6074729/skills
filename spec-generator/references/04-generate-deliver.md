# 阶段三至六：范围确认、生成、自检交付、Skills 推荐

## 3. 确认规范范围

用 `AskUserQuestion` 确认输出位置、输出形式、规则域、语言，以及是否把 Skills 推荐结果写入 README。Skills 推荐可以随交付报告，但不得在用户未选择时修改 README。

| 项 | 选项 |
|---|---|
| 输出位置 | 项目根目录 `AGENTS.md` + `.agents/rules/`（推荐）/ 自定义目录 |
| 输出形式 | 完整版（推荐）/ 仅 `AGENTS.md` / 单文件 `项目规范.md` |
| 语言 | 中文 / 英文 / 中英双语镜像（推荐） |
| README 更新 | 只在交付报告推荐（推荐）/ 追加到 README / 暂缓决定 |

单文件形式将所有已选规则域合并到 `项目规范.md`；仅 `AGENTS.md` 形式只生成该文件。启用任一工作流模式时，必须使用项目根目录 `AGENTS.md` + `.agents/rules/` 的完整版输出；单文件、仅 `AGENTS.md` 与自定义规范目录会使总控 Skill 的规则路由失效。遇到这些选择时，先让用户改为完整版与标准路径，或关闭工作流；不得静默扩大输出范围或省略工作流要求。工作流映射要求的规则域不可取消。

规则域按项目类型预选，用户可调整：

| 规则文件 | 全栈 | 仅前端 | 仅后端 |
|---|---|---|---|
| `architecture.md` | ✅ | ✅ | ✅ |
| `api-contract.md` | ✅ | 有 API 调用时 | ✅ |
| `backend.md` | ✅ | ❌ | ✅ |
| `database.md` | ✅ | ❌ | ✅ |
| `frontend-ui.md` | ✅ | ✅ | ❌ |
| `data-permission.md` | 需要时 | ❌ | 需要时 |
| `cache-consistency.md` | 需要时 | ❌ | 需要时 |
| `security.md` / `devops.md` | ✅ | ✅ | ✅ |
| `dev-tooling.md` / `testing.md` / `workflow.md` / `documentation.md` | ✅ | ✅ | ✅ |

表中规则域按项目类型和实际能力裁剪：全栈生成全部适用域；仅前端不生成后端、数据库、数据权限和缓存规则，客户端状态 / 请求缓存写在 `frontend-ui.md`；仅后端不生成前端 UI 规则。仅前端的 `api-contract.md` 仅在存在 API 调用时生成。数据权限 / 服务端缓存对全栈和后端项目按实际需求判定。`security.md`、`devops.md`、`testing.md`、`dev-tooling.md`、`workflow.md`、`documentation.md` 对三类项目都保留，但内容必须按该项目实际能力、用户决定和工作流模式裁剪。

## 4. 生成规范文档

### 4.1 生成依据

无需外部指南或固定模板。以本技能内置原则与规则域映射为设计边界；用户确认的目标定义规范期望状态；目标项目中可验证的代码、配置和现有规范用于描述当前状态与差距；阶段二动态检索的官方资料用于确认技术实现细节。不得把现状误当成用户的最终目标，不得把映射表中的示例技术栈或示例条目误当成项目事实，也不得伪造检索、代码或运行证据。

### 4.1-A 目标文件冲突

写入前逐个检查目标文件是否已存在。新生成意图遇到同名文件时，先保留原文件并向用户展示冲突与合并方案；用户确认后再改写。优化已有规范时，只改已确认的差异项，保留无关内容；不得整文件覆盖、删除或改写用户管理区块。任何写入失败或冲突未解决，都要保留原文件并在交付中标为阻塞项。

### 4.2 生成顺序（逐个落盘）

1. `AGENTS.md`
2. `architecture.md`
3. `api-contract.md`
4. `backend.md`
5. `database.md`
6. `frontend-ui.md`
7. `data-permission.md`（需要时）
8. `cache-consistency.md`（需要时）
9. `dev-tooling.md`
10. `testing.md`
11. `devops.md`
12. `security.md`
13. `workflow.md`
14. `documentation.md`

仅前端跳过 4/5/7/8，仅后端跳过 6。模板：`templates/AGENTS.template.md`、`templates/rule-file.template.md`；规则域映射与填充方法见 `templates/rule-domain-mapping.md`。

### 4.3 内容原则

**原则一：内置原则定边界，动态证据定内容。** 五大支柱、AI 行为规范与共性原则来自本技能；项目专属约束来自用户确认和可验证的项目事实；实现细节来自阶段二检索结果。禁止把示例当事实或臆造规范条目。

**原则二：技术栈替换点。** 只替换实现层：`{ext}` → 实际后缀；查询方式 → ORM 推荐 API；事务 → 框架事务 API；异常类 → 框架异常基类；全局异常处理 → 框架全局处理器；依赖注入 → 框架 DI；静态检查 → 项目 lint 工具；构建命令 → 项目构建脚本。取值以阶段二检索为准；`security.md`、`devops.md` 同样换成本栈实现，禁止沿用示例中的技术专名。

**原则三：命名。** 从目标项目现有命名与当前官方约定中归纳；框架强约定（如 `*.module.ts`、`*.controller.ts`、`*.service.ts`）优先并说明依据。项目没有可验证先例时，提出建议并交由用户确认。

**原则四：目录结构。** 按检索到的官方结构生成，说明各目录职责、模块内部组织、禁止跨目录访问边界。可用 CodeGraph `files` 校验目标项目真实目录。

**原则五：框架内置能力优先（强制，仅采用提供相应内置能力的框架时）。** 只在项目实际存在的层生成对应章节：前端框架 → `frontend-ui.md`；后端框架 → `backend.md`；使用 ORM → `database.md`；测试框架 → `testing.md`；构建工具 → `dev-tooling.md`。仅前端不得生成后端 / ORM 章节，仅后端不得生成前端 UI 章节。按 §3 的类型裁剪规则；模板是可选章节素材，不是要求所有项目生成全部章节。

禁止：未检索到清单就写组件名；把框架未提供的组件列为「必须使用」；规则违反指南禁止项；替代方案章节留空。

**原则六：公共模块抽离（强制）。** 用三同三异判定「该抽」还是「只是长得像」：

| 维度 | 必须相同 | 允许不同 |
|---|---|---|
| 流程 | 交互步骤、调用顺序、状态流转 | 标题、文案、样式 |
| 契约 | 输入输出结构、回调语义 | 接口地址、鉴权值、租户标识 |
| 边界 | 校验时机、失败处理、取消与重试 | 文件类型、大小上限、超时时间 |

满足任一即评估抽离：同构逻辑 ≥2 处且单处 ≥30 行；≥3 处且单处 ≥10 行；差异点 ≤5 个且均可转为配置、插槽或适配器参数。

禁止抽离：仅 1 处使用且无已确认复用；业务语义不同（如上传头像与上传合同附件的校验、审批、存储流程不同）；需 >5 个参数或 ≥2 个布尔开关（应先拆分能力）；差异改变控制流；假设性需求。

形态优先级：配置驱动的单一实现 → Hook / Service → 适配器 / 策略 → 基类（仅框架强制时）。落点：前端 `src/components/common/{domain}/` 或 `src/composables/`，后端 `src/modules/shared/{domain}/` 或 `internal/shared/{domain}/`；按能力命名，单一入口导出，禁止反向 import 业务模块。

上传示例：`components/common/upload/` 放 `UploadDialog.vue|tsx`（选择、校验、进度、重试）、`useUpload.ts`（编排与状态）、`types.ts`（UploadOptions）；调用点只传 `{ accept, maxSize, endpoint, extraFormData, onSuccess }`，禁止每页各写一份流程。

分层边界：基础设施模块（core/web/cache/oss/auth 等）按技术与依赖边界预设切分，不套用上述数量门槛；业务复用模块（上传、导入、导出流程）必须达到门槛才抽离；业务语义不得下沉到基础设施层。

验收：调用点只传配置；校验、请求、错误处理、重试只有一份；每个变体有测试；无反向业务依赖；改流程只改一处。

迁移：CodeGraph `explore` 或目录扫描标出重复点 → 取覆盖最全者为基准 → 抽出配置类型与默认值 → 逐点替换并删除旧实现 → 跑测试查反向依赖。与「禁止过度抽象」的边界：唯一放行条件是 ≥2 处真实复用 + 差异可配置化。

**原则七：自包含与引用审批（强制）。** 规范正文必须包含本文件适用的完整规则，禁止用「参见/详见某文件、某链接」替代应有正文。允许必要的路由引用（`AGENTS.md` 指向 `.agents/rules/workflow.md`）及检查入口（启用工作流模式时引用 `.ai-workflow/required-checks.md`），但被引用文件仍须自包含，引用不得替代规则正文。来源标注用的外部 URL 不受此限；其他项目文本文件引用须先经用户同意，用户未同意不得写入。

**原则八：工作流为骨（仅启用工作流模式时）。** 规范必须以所选模式实际包含的流程为基础生成，而不是先出通用模板再外挂流程。完整模式按 `05-workflow-mode.md` §3.5.6-C 写入 OpenSpec / Superpowers 的实际闭环；轻量模式只写已配置的本地计划、测试、命令和门禁，不得写入未安装能力。`workflow.md` 写流程主干，`testing.md` 写适用的测试规则，`dev-tooling.md` 写实际工具命令，`documentation.md` 写实际存在的规格目录与教程落点，`architecture.md` 写影响面分析前置，`security.md` / `devops.md` 把权限与迁移审查纳入门禁；`AGENTS.md` 只保留受管区块与路由。开关关闭时，任何规则文件不得出现 OpenSpec、Superpowers、`.ai-workflow/` 内容。

项目类型和工作流模式的交叉裁剪：

| 单项目类型 | 工作流关闭 | 完整模式 | 轻量模式 | 自定义模式 |
|---|---|---|---|---|
| 全栈 | 生成前后端共有及两侧适用规则，不写工作流工具 | 规格审批、TDD、项目门禁、Ponytail、风险 gstack 与收尾闭环；门禁覆盖前后端实际存在的能力 | 本地计划和所选门禁；不带规格闭环或完整模式依赖 | 仅生成已确认阶段，门禁覆盖用户选择的前后端范围 |
| 仅前端 | 跳过后端 / 数据库 / 数据权限 / 缓存规则；API 规则仅在确有调用时生成 | 使用完整流程，但门禁只查 UI、客户端安全、构建和实际 API 契约；不运行数据库迁移 / 后端检查 | 本地流程和实际前端检查；不带规格闭环或完整模式依赖 | 按用户选择阶段生成，只含前端规则与门禁 |
| 仅后端 | 跳过前端 UI 规则；按实际数据库 / 权限 / 缓存情况生成后端规则 | 使用完整流程，但门禁只查 API、服务端安全、实际数据库变更和后端验证 | 本地流程和实际后端检查；不带规格闭环或完整模式依赖 | 按用户选择阶段生成，只含后端规则与门禁 |

这里的「全部项目」是多项目范围，不等同于单个全栈项目。多项目目录或 Monorepo 对每个目标项目分别应用本表；根级共享规则 / CI 只记录一次并明确覆盖范围。完整模式若用户选择不新增测试但项目又没有可执行测试能力，须先解决冲突，不能把 TDD 标成已完成；不论类型，CI/CD 都依据逐项目确认生成。

### 4.4 AGENTS.md 结构

项目名称与定位 → 顶级规范要求（定位、核心边界、接口性能）→ AI 行为规范（5 项禁止，完整保留）→ AI 行为门禁 → 外部规则文件声明 → 通用强制规则 → 各领域规范域（含触发场景列表）。

`templates/AGENTS.template.md` 是全栈超集。生成时必须删除所有不适用的章节、触发场景、规则文件链接和占位符：仅前端不能留下 `backend.md`、`database.md`、`data-permission.md`、`cache-consistency.md` 的引用，也不能把服务端授权、SQL 或 ORM 当成本项目职责；仅后端不能留下 `frontend-ui.md` 的引用；条件生成的 `api-contract.md` 也不得被其他章节无条件引用。顶层性能要求须改为该项目实际层次的性能约束，不能向纯前端项目要求数据库批量查询。`security.md`、`devops.md` 的内容也须按实际边界改写；例如前端只规定客户端安全和实际发布产物，不把 UI 权限显隐说成服务端授权，不为静态站点虚构健康探针。最终检查每个链接目标真实存在，且触发条件与项目类型一致。

### 4.5 规则文件结构

规则域名 → 适用范围 → 核心要求（项目事实 + 用户确认 + 动态检索的技术实践）→ 复用与抽离要求（命中公共模块时）→ 验证要求（技术栈可执行的命令）→ 审查要求。

## 5. 自检与交付

### 5.1 自检

执行 `templates/checklist.md`，按项目类型取适用项，覆盖：AI 行为、治理架构、技术栈适配、框架组件、架构、接口性能、代码实现、数据库缓存、测试、文档、跨平台工具链、最佳实践来源、语言规范、预检、动态学习、交付完整性、Skills 推荐、阶段零意图与本地技能。

### 5.2 交付内容（9 项）

1. 任务意图摘要
2. 文件清单（clickable file links）
3. 技术栈摘要
4. 最佳实践来源（Context7 库 ID / URL / 代码图证据）
5. 本地技能清单与引用位置（若集成）
6. 待定项与「待补充」项
7. 使用指南
8. 检查清单报告（表格）
9. Skills 推荐预告

### 5.3 格式

文件路径用 `[文件名](/绝对路径/文件名)`；来源用超链接；自检报告用表格；语言与用户一致（默认中文）。

## 6. 从 skills.sh 推荐 Skills

前置：意图 1–3 必须先通过阶段五自检；意图 4「仅推荐 Skills」跳过阶段五，改为先完成 `02-stack.md` §1.0-B 轻量技术栈预检，再按本节 §6.3 完成推荐质量检查。来源限定 `https://www.skills.sh/`，禁止其他来源。

### 6.1 并行检索

按维度分工（按项目类型过滤）：后端 `backend`、`NestJS`、`API`；前端 `frontend`、`Vue`、`design`；数据库 `database`、`SQL`、`ORM`；测试 `tdd`、`test`、`e2e`；部署 `deploy`、`Docker`、`build`；代码质量 `review`、`refactor`、`security`；文档协作 `docs`、`triage`、`handoff`。

仅当阶段零允许子代理并行且执行环境提供子代理能力时，才并行分派检索。否则由主流程串行完成相同检索；不得把用户关闭的子代理开关当作工具不可用并擅自重开。分派时每个任务包含：技术栈、项目类型、检索目标、检索方式（`WebFetch` 排行榜 + `WebSearch` site 查询 + `WebFetch` 详情页）、输出字段（名称、仓库、安装命令、用途、场景、链接）、每维度 3-5 个。

### 6.2 README 更新

生成规范的意图在阶段三确认 README 选项；「仅推荐 Skills」意图因跳过阶段三，必须在本节先询问：只在交付报告推荐（推荐）/ 追加到 README / 暂缓决定。只有用户明确选择追加时才修改或新建 README；未同意时将推荐作为交付内容，不写入项目文件。若存在 `README.zh-CN.md`，仅在用户同意写入 README 后同步更新。

表结构（每维度一张表，表头只写一次）：

```markdown
## {维度中文名}
| Skill 名称 | 所属仓库 | 安装命令 | 用途 | 适用场景 |
|---|---|---|---|---|
| {name} | {owner/repo} | `npx skills add {owner/repo}` | {用途} | {场景} |
```

存在 `README.zh-CN.md` 时同步更新；中文文档中的表头与说明必须为中文。

### 6.3 质量要求

相关性高、当前活跃、每维度 3-5 个、字段完整、优先高安装量；禁止推荐非 skills.sh 来源、无关、废弃或未验证的 skills；不得向 README 添加无关内容。

## 7. 异常处理

| 场景 | 处理 |
|---|---|
| 检索失败 | 告知缺失维度，按通用经验生成并标注「未经最新实践验证」，建议后续补检 |
| 技术栈待定 | 使用 `{待定：需根据实际采用的{维度}补充}`，交付时汇总 |
| 与项目证据或用户意图冲突 | 写明冲突，按用户确认和可验证事实处理；技术细节标注资料依据 |
| 组件清单不完整 | 标注 `{待补充：需查{框架}官方文档}`，禁止臆造 |
| 子代理失败 | 主流程 `WebFetch` 排行榜 → `WebSearch site:skills.sh`；仍失败输出 `RECOMMENDED-SKILLS.md` |
| 本地技能异常 | 跳过问题文件、说明原因、提供跳过路径，不阻塞主流程 |
