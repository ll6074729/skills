# 阶段二：深度检索与代码图分析

目标：用**版本化文档 + 代码结构图**替代整页抓取与源码通读，产出可追溯的「技术最佳实践摘要」与「组件清单」。

## 3.0 工具开关（先读阶段零记录）

| 开关 | 开 | 关（原流程） |
|---|---|---|
| Context7 | 按 3.1 两步协议取文档 | 全部改用 WebSearch（关键词含年份）；仍不足时 WebFetch 单页单章节 |
| CodeGraph | 按 3.2 三步协议取结构 | 全部改用 Glob + 定向 Read；参考项目只读目录与关键文件 |
| 子代理并行 | 按技术维度并行 | 主流程串行检索 |

开关为关时禁止调用对应工具，也不得在交付物中标注「需 MCP 在线」；其余流程与产物结构保持不变。

## 3.1 Context7 调用逻辑（首选文档源）

**接入位置**：阶段一每个维度的确认前、阶段二每项技术的最佳实践、阶段四组件与 API 清单。

**两步协议**：

1. `resolve-library-id`：`libraryName` 传技术名（`nestjs`、`vue`、`typeorm`、`prisma`、`vitest`），`query` 传当前要解决的问题（如 `dependency injection`）。只保留返回中与项目栈匹配的 1 个 library ID。
2. `query-docs`：`libraryId` 用第 1 步结果，`topic` 用下表窄主题；一次只问一个主题。

| 需求 | topic 取值 |
|---|---|
| 目录结构 / 模块组织 | `project structure`、`modules` |
| 依赖注入 / 容器 | `dependency injection`、`providers` |
| 中间件 / 守卫 / 拦截器 | `middleware`、`guards`、`interceptors` |
| 数据访问 / 事务 | `repository`、`transactions`、`migrations` |
| 异常 / 日志 / 配置 | `exception filters`、`logging`、`configuration` |
| 测试 / Mock / 覆盖率 | `testing`、`mocking`、`coverage` |
| 组件使用 | `components`、`forms`、`tables`、`icon` |
| 构建 / 部署 | `build`、`deployment` |

**约束**：

- 每个 library ≤3 次查询；同一 library 同一主题不重复；命中即停。
- 每次返回先抽取 3-7 条要点（命令、API 名、配置键），丢弃示例长文与营销段落。
- 只查项目已确认的技术，禁止为「可能的未来技术」做预检索。
- 失败或无结果：转 `WebSearch`（关键词含当前年份）；再无结果标注「未验证」。

**摘要条目格式**（进入上下文的最小单元）：

```
[{技术}] {主题} | 版本 {x.y} | 来源 context7:{libraryId}/{topic} | {日期}
要点：{3-7 条}
用于：{目标规则文件与章节}
```

## 3.2 CodeGraph 调用逻辑（首选代码结构源）

**接入位置**：

| 场景 | 用途 |
|---|---|
| 阶段一预检补充 | 配置缺失或仓库较大时，识别框架、入口、目录职责 |
| 阶段二参考项目分析 | 提取组件使用约定、目录组织、调用路径，替代 clone 后通读源码 |
| 优化已有规范 | 比对现有代码与规范差距（哪些约定已落地、哪些缺失） |
| 阶段四 | 校验规范中引用的模块/路径真实存在 |

**索引准备**（一次）：

```bash
node scripts/codegraph.mjs ensure --project <repo-path>
```

内部逻辑：`.codegraph/` 存在则 `codegraph sync`，否则 `codegraph init`；失败返回非 0 并输出原因，由调用方降级。已索引项目禁止重复 init。

**查询序列**（MCP 优先）：

1. `codegraph_status`：确认索引可用、文件数、语言分布（不读源码）。
2. `codegraph_explore(query, path)`：一次问一个结构化问题，例如 `"table component usage"`、`"dependency injection modules"`、`"request client interceptor"`。
3. `codegraph_node(symbol)`：仅当 explore 摘要不足时，取单个符号源码与上下游。

CLI 等价命令：`codegraph explore "<query>" --path <repo> --max-files 3`、`codegraph node <symbol> --path <repo>`、`codegraph query <symbol>`、`codegraph files`。

**约束**：

- 每次 explore ≤3 个文件；只记录「约定 + 路径 + 1 个代表性符号」，不粘贴大段源码。
- 问题必须是业务能力，不是文件名猜测；一次一个主题，禁止宽泛查询（如 `"everything"`）。
- 结果用于**佐证**规范条目，不直接作为规范文本；需与技能内置原则、用户确认和项目证据交叉核对。
- MCP 不可用时用 CLI；CLI 不可用时降级 `Glob` + 定向 `Read`（单文件 ≤200 行），并标注「代码图为启发式结果」。

**提取产物格式**：

```
[{项目}] {能力} | 证据 {文件路径:符号} | 约定：{命名/分层/调用方式}
建议写入：{规则文件/章节}
```

## 3.3 参考项目深度分析（强制，用户选了参考项目时）

1. **规范模式**：WebSearch `{project} project conventions`、`{project} AGENTS.md rules`；`WebFetch` 取 README / AGENTS.md / `.agents/rules/`（若存在）。
2. **结构调整**：CodeGraph `explore` 回答：目录分层、模块入口、组件注册方式、请求层封装、状态管理组织。
3. **组件约定**：CodeGraph `explore "component usage"` + `node` 取 1-2 个代表组件，记录组件名、配置方式、禁止替代写法。

产出「参考项目规范模式摘要」，每条带路径证据；无证据的推测不得写入规范。

## 3.4 本地技能素材合并（意图 3 时）

- 将本地技能中的规则条目、约束、组件清单与检索结果**按主题归并**，同一主题只保留信息量更大的表述。
- 每条本地素材标注「本地技能：{技能名}（{路径}）」。
- 与检索结果冲突：按用户确认、可验证项目事实和技能内置原则核对；仍冲突则并列说明并告知用户。
- 本地技能只进素材层，不改技能内置原则，不生成独立规则域。

## 3.5 框架内置组件清单标准化

| 功能场景 | 必须使用的内置组件 | 配置方式 | 禁止替代方案 |
|---|---|---|---|
| {表格页面} | {表格组件 + 分页组件} | {props/插槽} | {自行封装表格 / 第三方表格库} |
| {表单} | {表单组件} | {校验与布局配置} | {自封装表单} |
| {弹窗/抽屉} | {弹窗组件 / 抽屉组件} | {受控方式} | {自实现遮罩层} |
| {操作列} | {按钮 + 确认组件} | {权限与二次确认} | {手写按钮组} |
| {上传/下载} | {上传组件 / 下载方法} | {分片、鉴权} | {原生 fetch 拼装} |
| {图标} | {图标组件} | {命名格式} | {散落 SVG} |

后端能力清单同理：DI 装饰器、守卫/拦截器基类、数据访问方式、异常基类、日志组件、配置读取方式，各列「必须使用 / 禁止替代」。

每条清单标注来源：`context7` / `官方文档 URL` / `参考项目路径` / `用户提供`。缺失项写 `{待补充：需查 {framework} 官方文档}`，禁止猜组件名。

## 3.6 结果处理与冲突

- 检索不足：告知用户该维度基于通用经验生成，标注「未经最新实践验证」。
- 组件清单不完整：交付时汇总「待补充」项。
- 与项目证据或用户意图冲突：写明冲突点；由用户确认项目目标，技术细节依据当前官方资料，并记录取舍。
- 框架组件规则不得违反「禁止过度抽象」「禁止无需求支撑的转发型抽象」。
- 所有摘要必须落入对应规则文件章节，不得只停留在对话中。
